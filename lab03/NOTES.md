## Этап 2. Сравнение версий и поиск изменений

### git log, git diff, git show — в чём разница

- `git log` — показывает список коммитов с сообщениями и метаданными.
  Не показывает содержимое изменений.
- `git diff` — показывает разницу между двумя состояниями (коммитами,
  индексом, рабочей папкой). Не показывает метаданные.
- `git show` — показывает один конкретный коммит целиком: автора, дату,
  сообщение и diff этого коммита.

### Что нашли log -S и blame

- `git log -S"def"` искал коммиты, где появлялась или исчезала строка
  с `def`. Ничего не нашёл, потому что в `calc.py` нет функций с `def`.
- `git blame` показал, какая строка файла появилась в каком коммите
  и кем добавлена.
## Этап 3. Восстановление файла

### git restore и git restore --source

- `git restore <файл>` — восстанавливает файл из индекса (обычно
  из последнего коммита). Затирает изменения в рабочей папке.
- `git restore --source=<коммит> <файл>` — восстанавливает файл
  из указанного коммита. Например, `--source=HEAD~2` вернёт
  версию двухкоммитной давности.

### Что было бы с моими правками

Если бы я удалил строки и не сделал `git restore`, удаления остались бы
в рабочей папке и попали бы в следующий коммит. `git restore` их
затирает безвозвратно. При `--source=HEAD~2` я временно вернул старую
версию в рабочую папку — индекс и коммиты не менялись.

## Этап 4. Отмена ошибочного коммита

### git revert

`git revert HEAD` создаёт новый коммит, который отменяет изменения
указанного коммита. Ошибочный коммит не удаляется из истории —
рядом появляется коммит с обратными изменениями.

### Чем revert отличается от git reset --hard

- `git revert` добавляет новый коммит с обратными изменениями.
  История не переписывается. Безопасно для опубликованных коммитов.
- `git reset --hard <коммит>` удаляет все коммиты после указанного.
  История переписывается. Опасно, если коммиты уже на GitHub.

### Почему revert безопаснее

Если коммит уже на GitHub, `reset` потребует `push --force`, что
сломает копии у других. `revert` не трогает прошлое — только
добавляет новое.


## Этап 5. Тег рабочей версии

### Что такое тег

Тег — постоянное имя для коммита. В отличие от ветки, тег не двигается
при новых коммитах. По тегу можно через полгода найти версию v1.0.

### Чем тег отличается от ветки

- Ветка — подвижный указатель, двигается при новых коммитах.
- Тег — неподвижный указатель, всегда на одном коммите.

### Отправка тега на GitHub

`git push` не отправляет теги. Нужно явно: `git push origin v1.0`.

## Этап 6. Эксперимент в ветке

### Зачем ветка

Рискованные правки делают не в main, а в отдельной ветке. Если
эксперимент удался — ветку сливают в main через `git merge --no-ff`.
Если не удался — ветку удаляют, main остаётся нетронутой.

### Что я сделал

Создал ветку experiment, добавил безопасное деление с проверкой нуля,
закоммитил. Вернулся в main, слил ветку через --no-ff, удалил ветку.

### --no-ff

Без --no-ff Git мог бы просто передвинуть main вперёд (fast-forward),
и следа ветки не осталось бы. С --no-ff создаётся merge-коммит
с двумя родителями.
